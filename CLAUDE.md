# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A React + Vite single-page app simulating an IoT/embedded cybersecurity training sandbox ("Weak MQTT Auth" scenario). Students perform recon/exploitation against a simulated ESP32 + MQTT broker device ("Hack Mode"), then remediate the firmware ("Build Mode"), and professors review performance metrics ("Dashboard"). This is currently a **low-fidelity frontend prototype** — there is no backend, no real device, no real MQTT broker, and no persistence; everything is simulated client-side with in-memory React state and fabricated/seeded data.

## Commands

```
npm run dev       # start Vite dev server with HMR
npm run build     # production build to dist/
npm run preview   # preview the production build
npm run lint      # eslint over the whole repo
```

There is no test suite configured in this repo.

## Architecture

**Single-file screen router.** `src/App.jsx` holds all top-level state (`screen`, `role`, `registry`, `student`, `evalStudent`, `professor`, `overlay`, `menuOpen`) and renders one of the screen components below based on a `screen` string — there is no router library. Screens communicate purely through callback props (`onBack`, `onMenu`, `onNext`, etc.) passed down from `App.jsx`; there is no context or global store.

Screen flow: `RoleSelect` → (`StudentAccess` | `ProfessorAccess`) → `MainMenu` → (`HackMode` | `BuildMode` | `Dashboard`). `HackMode` and `BuildMode` link to each other directly. `Dashboard` is reachable both from a student's own `MainMenu` (evaluating themselves) and from `ProfessorAccess` (evaluating any registered student), which is why it takes a `role` prop that changes its back-navigation target and enables/disables the "next student" control.

**Screens** live in `src/screens/`, one file per screen, each a default-exported component taking navigation callbacks + data as props. **Shared components** (`AppHeader`, `InfoBanner`) live in `src/components/`.

**All simulated/seeded data lives in `src/data.js`**: `STUDENTS` (48 procedurally generated student records with metrics/logs, index 0 is the fixed demo student "Juan Dela Cruz"), `SCENARIOS`, `GUIDED_STEPS`. When changing seeded/demo content, edit this file rather than hardcoding values in screens. Build Mode's firmware project is no longer here — it is backend-sourced (see below).

**Hack Mode's terminal is not xterm.js** — despite `@xterm/xterm` and `@xterm/addon-fit` being dependencies in `package.json`, `HackMode.jsx` implements its own lightweight terminal via a `lines` state array rendered as styled `<div>`s, with canned command responses keyed by tool id (`nmap`, `sub`, `pub`, `cap`, `exp`) in a `responses` map. Free-text input is pattern-matched by substring in `submitCommand`.

**ESP32 device detection is a shared platform layer that neither mode owns** (`backend/app/hardware/`). The architecture is `ESP32 → Arduino CLI detection → Shared Device State → Build Mode / Hack Mode`. `app/hardware/state.py` holds the passive, dependency-free `DeviceState` (`connected`, `port`, `board`, `fqbn`, `identified`, `detail`, `checked_at`) and the one `DeviceStatus` vocabulary for the whole backend — `HardwareStatus` in `app/build/models.py` is an **alias of that same enum object**, not a parallel declaration, so the two modes cannot describe one board with different words. `app/hardware/monitor.py`'s process-wide `device_monitor` owns the current state: `snapshot()` is a lock-free read (the state is a frozen dataclass replaced wholesale), `refresh()` runs detection under a lock so concurrent polls from several sessions collapse into **one** `arduino-cli board list`, and `publish()` folds in a detection someone else already ran. It contains no Arduino CLI knowledge of its own — it reuses `app/build/flasher.py`'s existing `detect_devices`/`parse_board_list`/`_select_candidates` through a narrow `DeviceDetector` protocol (`run_flash` is deliberately out of view, so the shared layer structurally cannot upload anything). The build-layer import is lazy (`_detection_api`) purely to keep `app.build.models → app.hardware` from closing an import cycle.

**Panel identity comes from the ESP32's MAC.** `arduino-cli board list` only describes the USB *bridge* (a CP2102 whose `serialNumber` is a generic "0001"), so the chip's OTP-ROM MAC is the only durable per-panel id. `app/hardware/identity.py` reads it with the **esptool the ESP32 Arduino core already bundles** — the same binary `arduino-cli upload` drives, discovered under the Arduino15 data dir (override: `TRAINER_ESPTOOL_PATH`), invoked as a backend-built argv through `app/build/process.py` like every other tool. `app/hardware/panels.py` maps MAC → panel name (`20:9b:a9:88:0b:e4` → `SMART HOME MQTT CONTROL SYSTEM`; extend via the table or `TRAINER_PANEL_NAMES`); an unmapped board resolves to `None` so the UI shows the MAC rather than inventing a station name. **Probing is intrusive, so it is rare**: a MAC read drives the board into its bootloader and hard-resets it, so the monitor caches it per port (probed once per plug-in, not once per poll), clears it on disconnect, and `hold_identity_probe()` — which `flash_workspace` wraps its upload in — suppresses it entirely while a flash owns the port. `publish()` never probes. A monitor built over an *injected* detector gets `NullIdentityProbe`, so a fake device view can never drive real esptool at a real board.

Both modes poll on the same 10s interval and render **one uniform header** through one component, `src/components/HardwareHeaderStatus.jsx`: `HACK MODE | PANEL: … | USB: … | CONNECTED` / `BUILD MODE | …` — the mode name is the only difference. PANEL and USB are click-to-cycle **display-only** toggles, cycling `port_aliases` / MAC ↔ panel name; clicking changes no device state and sends no frame.

**The canonical trainer serial path** (`app/hardware/serial_alias.py`) is the USB field's alternate representation and the vocabulary the courseware uses. The trainer deploys to a Raspberry Pi, so the instructional Hack Mode commands speak `/dev/ttyUSB0` (`TRAINER_CANONICAL_SERIAL_ALIAS`) no matter what the dev host enumerates the same board as — `port_aliases` is therefore `(actual port, CLI label if different, canonical path)`, deduplicated, so Windows shows `COM3 ↔ /dev/ttyUSB0`, a Pi already on `/dev/ttyUSB0` shows one value, and a Pi on `/dev/ttyACM0` shows `/dev/ttyACM0 ↔ /dev/ttyUSB0`. **It is a label, never a device**: `DeviceState.port` always holds the real detected port, nothing opens or flashes to the canonical path, and `resolve_serial_target(target, state)` — the seam the later Hack serial engine plugs into — maps a student's canonical target back to `DeviceState.port` *before* any serial I/O, returning None rather than guessing when it matches neither. The build/flash path never reads aliases at all (it uploads to the port discovery returned). `SerialDevice.vid`/`pid` remain parsed as backend diagnostics but are deliberately not student-facing. The status field collapses the backend's richer internal vocabulary to only `CONNECTED`/`DISCONNECTED`, reports the **ESP32 and never the WebSocket**, and shows `—` for both fields when nothing is attached. Build Mode's `state.hardware` block and Hack Mode's `hardware` frame now carry the *identical* `DeviceState.snapshot()` payload, which is what lets one component render both. Hack Mode's frame is **dedicated** precisely so polling is **silent** — never xterm.js output, a `ScenarioEvent`, scenario state, or a router dispatch; `tests/test_websocket_hardware.py` asserts that frame-by-frame. Board-name fallbacks stay backend-side and per-mode (Build Mode its project board, Hack Mode `config.HARDWARE_BOARD_LABEL`). `DeviceState.port` is what Hack Mode's serial transport opens (below).

**Hack Mode's terminal talks to the real ESP32 over USB serial** (Phase 2A, `backend/app/hardware/serial_transport.py`). The path is `xterm.js -> /ws/hack -> command router -> SerialTransport -> pyserial -> ESP32`, and back. `SerialTransport` is per-session (`HackSession.serial`), opens nothing until a command asks, and reads on a **dedicated thread** that parks in the OS driver — pyserial is blocking and has no asyncio interface, so this is what keeps the event loop free; writes go through `asyncio.to_thread`. Bytes surface as `SerialEvent`s on a bounded queue (oldest dropped under flood); `app/websocket.py`'s `_pump_serial` task drains it, decodes through one stateful `SerialTextDecoder` (reassembling a CRLF or a UTF-8 char split across reads, normalising to CRLF for raw-mode xterm) and forwards them as **ordinary `output` frames** — which is why the frontend needed no change at all. A lost board becomes one controlled notice line, never an exception.

Four commands, registered in the same closed allowlist as every simulated tool: `serial-status` (read-only, opens nothing), `serial-monitor`, `serial-send <text>`, `serial-close`. They are the first `async def` handlers — `CommandRouter.dispatch` awaits a handler result if it is awaitable, so the eight synchronous simulated tools were untouched. A student may name the canonical `/dev/ttyUSB0`, but `serial_common.resolve_target` maps it through `resolve_serial_target` to the **real `DeviceState.port`** before the transport sees it; an unresolvable target is refused rather than guessed.

**STILL NOT A SHELL.** Serial input reaches a UART and nothing else. The parser already rejects shell metacharacters and control characters, the registry is a closed table, and no module on this path may use `subprocess`/`eval`/`exec`/`shell` — `tests/test_hack_backend.py`'s repo-wide scan covers the new modules with no exemption, and `tests/test_serial_transport.py` re-asserts it for the transport specifically. A payload like `"rm -rf /"` is transmitted as inert bytes; what the firmware does with them is the firmware's business.

**TEARDOWN MUST NOT AWAIT.** The server cancels the endpoint task on disconnect, so every `await` in the cleanup `finally` raises `CancelledError` immediately and abandons the rest. An earlier version awaited and therefore leaked both the serial port (blocking Build Mode from flashing that board) and the session registry entry. Cleanup is now three synchronous calls — `pump.cancel()`, `SerialTransport.release()`, `SessionManager.discard()` — and `tests/test_serial_commands.py` pins that.

**Validation still does not exist**, and neither do the later Hack phases: no MQTT suite, no nmap implementation, no firmware extraction/analysis, no scoring. The simulated scenario engine is untouched and still drives every non-serial command.

**Build Mode is a real backend-backed workspace with real compilation, not a mock.** `BuildMode.jsx` connects to `/ws/build` via `src/hooks/useBuildSocket.js`. The backend (`backend/app/build/`, `backend/app/build_sessions.py`, `backend/app/build_websocket.py`) owns one project per session, represented as an ordered sequence of locked/editable regions (`backend/app/build/models.py`, `workspace.py`). The default project a fresh session loads is the **LED Blink pipeline-proof project** (`backend/app/build/blink.py`, project id `led-blink-poc`) — a deliberately trivial one-file, one-editable-region firmware whose only job is to prove the write → compile → flash → physical-execution pipeline works end to end against a real ESP32. The earlier Environmental Monitoring / Weak MQTT firmware (`backend/app/build/environmental.py`, `create_environmental_monitoring_project`) predates the finalized five-panel scope and is no longer loaded by default; the module remains in the codebase, unused, for when that scope resumes. Only the one editable region can be edited (named `security_logic` on the environmental project, `blink_program` on the current default); the backend rejects any attempt to edit a locked region or an unknown region id, regardless of what the frontend sends. A `compile` request runs the real `arduino-cli` (`backend/app/build/compiler.py`, which builds the argument array and hands it to `backend/app/build/process.py` — the one module in the whole backend allowed to spawn a process, and the one both the compiler and the flasher go through) against a throwaway materialized copy of the workspace — `compile_status` moves through `not_started`/`running`/`succeeded`/`failed` for real, driven by the actual compiler exit code, and `compile_output` carries its real stdout/stderr back to the UI.

A `flash` request runs the real `arduino-cli upload` (`backend/app/build/flasher.py`) against a **physically connected ESP32**, so it needs real hardware attached. The backend discovers the serial device itself via `arduino-cli board list` and never lets the frontend name a port, executable, binary, or flag — the `flash` frame is field-less. Flashing requires a successful compile whose retained build output still matches the workspace by content hash (`BuildSession.flash_ready`), so editing the region after a green build disables flashing until it is compiled again. `flash_status` adds two members `compile_status` does not have: `detecting`, and `no_device` as a terminal state distinct from `failed`, because "no ESP32 is plugged in" must never be presented as a build or toolchain problem. A successful flash means the upload process exited 0 — nothing more.

Validation is still not implemented: nothing connects to MQTT, reads sensors, re-runs Hack Mode, or checks whether the remediation actually works. `validation_status` stays always `"not_started"`, and the Validate/Security-Test controls in the UI are disabled placeholders.

**Dashboard charts are hand-rolled inline SVG/CSS** (`BarChart`, `LineChart`, `RadarChart` inside `Dashboard.jsx`) — no charting library is used.

**Styling**: a single global `src/App.css` (~800 lines) plus a small `src/index.css` reset. No CSS modules, no Tailwind, no styled-components — class names are plain strings shared across screens (e.g. `.page`, `.panel`, `.btn-solid`, `.link-footer`).

**No routing library, no state management library, no backend/API calls.** Login, registration, and evaluation "lookups" are all synchronous in-memory array searches against `registry` (in `App.jsx`) or `STUDENTS` (in `data.js`) — nothing is persisted across a page reload.
