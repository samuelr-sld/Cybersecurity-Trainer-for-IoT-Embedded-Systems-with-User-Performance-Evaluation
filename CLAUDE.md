# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A React + Vite single-page app simulating an IoT/embedded cybersecurity training sandbox ("Weak MQTT Auth" scenario). Students perform recon/exploitation against a simulated ESP32 + MQTT broker device ("Hack Mode"), then remediate the firmware ("Build Mode"), and professors review performance metrics ("Dashboard"). This is currently a **low-fidelity frontend prototype** — there is no backend, no real device, no real MQTT broker, and no persistence; everything is simulated client-side with in-memory React state and fabricated/seeded data.

## Commands

```
npm run dev       # start Vite dev server with HMR
npm run build     # production build to dist/
npm run preview   # preview the production build
npm run lint      # eslint over the whole repo
```

There is no test suite configured in this repo.

## Architecture

**Single-file screen router.** `src/App.jsx` holds all top-level state (`screen`, `role`, `registry`, `student`, `evalStudent`, `professor`, `overlay`, `menuOpen`) and renders one of the screen components below based on a `screen` string — there is no router library. Screens communicate purely through callback props (`onBack`, `onMenu`, `onNext`, etc.) passed down from `App.jsx`; there is no context or global store.

Screen flow: `RoleSelect` → (`StudentAccess` | `ProfessorAccess`) → `MainMenu` → (`HackMode` | `BuildMode` | `Dashboard`). `HackMode` and `BuildMode` link to each other directly. `Dashboard` is reachable both from a student's own `MainMenu` (evaluating themselves) and from `ProfessorAccess` (evaluating any registered student), which is why it takes a `role` prop that changes its back-navigation target and enables/disables the "next student" control.

**Screens** live in `src/screens/`, one file per screen, each a default-exported component taking navigation callbacks + data as props. **Shared components** (`AppHeader`, `InfoBanner`) live in `src/components/`.

**All simulated/seeded data lives in `src/data.js`**: `STUDENTS` (48 procedurally generated student records with metrics/logs, index 0 is the fixed demo student "Juan Dela Cruz"), `SCENARIOS`, `GUIDED_STEPS`. When changing seeded/demo content, edit this file rather than hardcoding values in screens. Build Mode's firmware project is no longer here — it is backend-sourced (see below).

**Hack Mode's terminal is not xterm.js** — despite `@xterm/xterm` and `@xterm/addon-fit` being dependencies in `package.json`, `HackMode.jsx` implements its own lightweight terminal via a `lines` state array rendered as styled `<div>`s, with canned command responses keyed by tool id (`nmap`, `sub`, `pub`, `cap`, `exp`) in a `responses` map. Free-text input is pattern-matched by substring in `submitCommand`.

**ESP32 device detection is a shared platform layer that neither mode owns** (`backend/app/hardware/`). The architecture is `ESP32 → Arduino CLI detection → Shared Device State → Build Mode / Hack Mode`. `app/hardware/state.py` holds the passive, dependency-free `DeviceState` (`connected`, `port`, `board`, `fqbn`, `identified`, `detail`, `checked_at`) and the one `DeviceStatus` vocabulary for the whole backend — `HardwareStatus` in `app/build/models.py` is an **alias of that same enum object**, not a parallel declaration, so the two modes cannot describe one board with different words. `app/hardware/monitor.py`'s process-wide `device_monitor` owns the current state: `snapshot()` is a lock-free read (the state is a frozen dataclass replaced wholesale), `refresh()` runs detection under a lock so concurrent polls from several sessions collapse into **one** `arduino-cli board list`, and `publish()` folds in a detection someone else already ran. It contains no Arduino CLI knowledge of its own — it reuses `app/build/flasher.py`'s existing `detect_devices`/`parse_board_list`/`_select_candidates` through a narrow `DeviceDetector` protocol (`run_flash` is deliberately out of view, so the shared layer structurally cannot upload anything). The build-layer import is lazy (`_detection_api`) purely to keep `app.build.models → app.hardware` from closing an import cycle.

**Panel identity comes from the ESP32's MAC.** `arduino-cli board list` only describes the USB *bridge* (a CP2102 whose `serialNumber` is a generic "0001"), so the chip's OTP-ROM MAC is the only durable per-panel id. `app/hardware/identity.py` reads it with the **esptool the ESP32 Arduino core already bundles** — the same binary `arduino-cli upload` drives, discovered under the Arduino15 data dir (override: `TRAINER_ESPTOOL_PATH`), invoked as a backend-built argv through `app/build/process.py` like every other tool. Phase 2C.5 turned the MAC into a key rather than a meaning, and Phase 2D.1 extended the chain one link: **`MAC → PanelRegistry → PanelDefinition → PanelPackage → FirmwareConfiguration`**. `app/hardware/panels.py` holds `PanelDefinition` (`panel_id`, `display_name`, `mac_addresses`, `package_id`) and `PanelRegistry` (one normalized dict lookup for every panel — no `if panel_id ==` anywhere; construction rejects duplicate ids and a MAC bound to two panels). **`PanelDefinition` no longer carries `firmware`** — a definition answers only "which panel is this board?", and points at its experiment by a validated `package_id` (an identifier, never a path), so naming a panel stays a pure lookup off the 10s header poll. `BUILT_IN_PANELS` defines all five panels of the finalized scope; only `20:9b:a9:88:0b:e4` is bound (to `smart-home-mqtt-control`), and only that one panel references a package (`package_id=None` for the other four — the honest "no courseware yet" state). `TRAINER_PANEL_MACS` (`mac=panel-id`, replacing the old `TRAINER_PANEL_NAMES`) can re-bind an interchangeable module to an *existing* panel id, never create a panel or attach a package. An unregistered board resolves to `PanelMatch.UNREGISTERED`, so the UI shows the MAC rather than inventing a station name. `app/hardware/firmware.py`'s `FirmwareConfiguration` (source `BUILD_PROJECT` id or relative `SKETCH_DIRECTORY`, board FQBN, compilation build properties, flashing, serial baud) is pure validated data that rejects path traversal and flag-shaped values; it is now consumed **through the package** rather than off the definition. `app/hardware/panel_identification.py`'s `PanelIdentificationService` delegates MAC acquisition to `DeviceMonitor` and lookup to the monitor's registry (`NOT_CONNECTED`/`UNIDENTIFIED`/`UNREGISTERED`/`IDENTIFIED`), and exposes the identified panel's `package_id` (not its firmware); **identifying a panel triggers nothing** — no compile, flash, provisioning, scenario, or event (that is a later phase). `normalize_mac` lives in the pure `app/hardware/mac.py` so the registry imports no I/O module; `tests/test_panel_registry.py` asserts those imports statically.

**A connected panel's *experiment* is a trusted resource package, loaded but never executed** (Phase 2D.1/2D.2, `backend/app/panels/`). The guiding split is **the engine provides the tools; the connected panel provides the experiment**: `app/commands/` keeps offering one global toolbox of real tools to every panel, and a package only says what a student should *do* with them. `app/panels/models.py`'s `PanelPackage` is frozen, validated data — `ScenarioDefinition` (which experiment, by `scenario_id` *key*), `LearningContent` (objectives, activity instructions, `ExpectedFinding`s), a `WorkflowStep` sequence (each naming a real global tool, validated to a bare command name — never a command line), an `EvaluationDeclaration` (`SuccessCondition`s citing the canonical Phase 2B `ScenarioEventType` vocabulary, plus which of the seven established metrics ACR/RE/EAC/TTE/TTR/AID/DEI are *relevant*), a reused `FirmwareConfiguration`, and scalar-only static `parameters`. It deliberately holds **no** target network facts (owned by the executable `ScenarioState`), no scenario behaviour, no display name (owned by `PanelDefinition`), and no metric formulas — so there is one source of truth for each. `app/panels/loader.py`'s `PanelPackageLoader` is the only filesystem-touching piece: one algorithm for every panel (`<root>/<package-id>/panel.json`, root = `TRAINER_PANEL_PACKAGE_ROOT`, default `backend/panels/`), strict about unknown keys, rejecting a missing package (`PanelPackageNotFoundError`) distinctly from an invalid one (`PanelPackageInvalidError`) and from declared-but-absent firmware (`FirmwareResourceMissingError`). It parses with `json.load` into dataclasses — **no `eval`/`exec`/`import`, no `subprocess`, no command dispatch, no build-layer import, no path from a client** (the `package_id` is a validated identifier, re-checked for containment); `tests/test_panel_packages.py` asserts all of that statically. `app/panels/service.py`'s `PanelResourceService` composes the existing identification service with the loader into one answer (`NOT_CONNECTED`/`UNIDENTIFIED`/`UNREGISTERED`/`NO_PACKAGE`/`PACKAGE_ERROR`/`READY`), and `PanelResources.firmware` is the single route to a panel's firmware configuration. **Loading a package triggers nothing** — no compile, flash, scenario start, event, or router dispatch. As of Phase 2D.4 the service is read on one request path (Hack Mode connect, to select the session's scenario — see below) and nowhere else: identification stays silent, the Hack Mode `hardware` frame is unchanged, and the frontend is untouched. Panel 1's package (`backend/panels/smart-home-mqtt-control/`, `panel.json` + a real `.ino` firmware resource under `firmware/`) is integrated; the complete Panel 1 attack/remediation/evaluation lifecycle, Panel 2's activity, and all metric computation are **not** — these are later phases the seam exists to feed.

**A declared `scenario_id` selects an executable `Scenario` through one explicit table, not a conditional chain** (Phase 2D.3, `app/scenarios/registry.py`). `ScenarioRegistry` maps `scenario_id → Scenario` factory the same way `PanelRegistry` maps a MAC to a panel: `create(scenario_id)` looks the id up and builds a **fresh** instance (per-session isolation preserved), `create_for_package(package)` reads only `package.scenario_id` (the package stays the one source of truth for *which* scenario a panel uses; `panel.json` is never re-read here), and an unregistered id raises `UnknownScenarioError` — **never** a dynamic import, `eval`/`exec`, or a module path built from the id. `build_default_scenario_registry()` seeds two ids, each resolving to its **own dedicated** implementation: `environmental-monitoring` → `EnvironmentalMonitoringScenario` (the default `create_default_scenario()` returns, a simulated BME280 telemetry target whose flaw is an unauthenticated publish topic), and `smart-home-mqtt-control` → `SmartHomeMQTTScenario` (Phase 2D.5, `app/scenarios/smart_home.py` + `smart_home_state.py`). Panel 1 is the Smart Home MQTT Control System — an ESP32 L293D motor controller on an **authenticated** broker whose command topic `capstone/panel1/motor` carries **no per-command authorization**, so a forged `START`/`STOP` is obeyed (the lesson is *authentication ≠ authorization*, a genuinely different security model from the Environmental target's, which is why it is its own class and imports none of that target's state). Phase 2D.5 replaced the earlier temporary mapping (which pointed this id at `EnvironmentalMonitoringScenario` to prove the wiring) by re-pointing this one registry entry — no selector, registry-algorithm, or generic-engine change; `tests/test_smart_home_scenario.py` covers it, including that the same router/parser/handlers drive it unchanged. Selection is passive — instantiating a `Scenario` is an in-memory construction that flashes nothing, opens no port, starts no experiment, and runs no command. Phase 2D.4 wires it into the Hack session lifecycle (below). `tests/test_scenario_selection.py` proves the default is preserved, Panel 1 resolves, an unknown id fails cleanly, an alternate scenario resolves through the unchanged algorithm, and the layer imports nothing that executes or flashes. **Probing is intrusive, so it is rare**: a MAC read drives the board into its bootloader and hard-resets it, so the monitor caches it per port (probed once per plug-in, not once per poll), clears it on disconnect, and `hold_identity_probe()` — which `flash_workspace` wraps its upload in — suppresses it entirely while a flash owns the port. `publish()` never probes. A monitor built over an *injected* detector gets `NullIdentityProbe`, so a fake device view can never drive real esptool at a real board.

**The attached panel's declared experiment reaches the session at connect** (Phase 2D.4, `app/scenario_selection.py`). This is lifecycle wiring only — it joins links that already existed and adds no behaviour of its own. `/ws/hack` now calls `select_session_scenario()` before `SessionManager.create`, and the full chain runs once per connection: `PanelResourceService.resolve()` (MAC → panel → package) → `default_scenario_registry.create_for_package(package)` → `SessionManager.create(scenario=...)` → `HackSession.scenario`. **The scenario is injected, never looked up by the session**: `HackSession` gained an optional constructor argument and still knows nothing of MACs, panel ids, package ids, `panel.json` or a resource root, and `app/sessions.py` imports none of those layers (asserted statically). The selector is its own module because the two halves may not import each other — `app.panels` is barred from importing `app.scenarios`, and `app/scenarios/registry.py` keeps `PanelPackage` behind `TYPE_CHECKING` — so their composition needs a third place. **There is no panel branch anywhere on the path**: the package names a `scenario_id`, the registry maps it to a class, and both are data. **Selection is a lookup, not an action** — it calls the passive `resolve()`, not `refresh()`, so a connect runs no `arduino-cli`, probes no MAC (a probe resets the board), opens no port, starts no MQTT, compiles/flashes/provisions nothing, emits no `ScenarioEvent`, records no activity row, and sends no frame; the wire protocol is byte-for-byte unchanged. **Failure is a selection, not an exception**: NOT_CONNECTED, UNIDENTIFIED, UNREGISTERED, NO_PACKAGE, PACKAGE_ERROR and a package naming an unimplemented `scenario_id` all yield the long-standing default `environmental-monitoring` scenario (the no-hardware development flow, explicitly preserved), with the reason logged rather than shown to the student — an unresolved board can never land on some *other* panel's experiment. Panel 1 therefore drives a real session through its own `scenario_id` today, but that id is still 2D.3's temporary mapping to `EnvironmentalMonitoringScenario`; **Panel 1's own tailored scenario does not exist** and re-pointing that one registry entry is what a later phase does. Because selection reads the monitor's cached state rather than detecting, **something has to fill that cache**: `app/main.py`'s lifespan starts `DeviceMonitor.prime()` (one `refresh()`, idempotent) as a background task at startup — not awaited, because a wedged USB driver would otherwise hold the backend unavailable for up to ~50s, and not on any request path. Until it completes, the state is `NOT_CHECKED`, which the panel layer now **propagates instead of flattening into NOT_CONNECTED** (`PanelIdentificationStatus.NOT_CHECKED` / `PanelResourceStatus.NOT_CHECKED`, a seventh member — the six existing ones are untouched). That distinction is the actual fix: `identify_panel` used to answer "no panel" for a board it had simply never looked for, so a session opened before the first poll fell back silently. `DeviceState.checked` is the primitive (False for the initial `NOT_CHECKED` and for a first `DETECTING` with no prior verdict). Its sibling `DeviceState.board_present` closes the same gap at the other end: `refresh()` publishes DETECTING via `replace(self._state, …)`, deliberately **retaining** the previous verdict's port/MAC/panel, but `connected` is `status is CONNECTED` and so reads False for that whole window — which made `identify_panel` report NOT_CONNECTED for a board mid-re-poll that had not gone anywhere. `board_present` reads the verdict that survives a re-check (during DETECTING, the retained `port`, which only a CONNECTED outcome ever sets), and `identify_panel` asks it instead of `connected`; `connected` keeps its instantaneous meaning for every other caller, and a completed detection replaces the state wholesale so nothing stale outlives it. `TRAINER_HARDWARE_STARTUP_DETECT=0` disables the startup detection; `tests/conftest.py` disables it for the suite so no TestClient spawns a CLI or resets a board. `tests/test_session_scenario_wiring.py` covers all of it.

Both modes poll on the same 10s interval and render **one uniform header** through one component, `src/components/HardwareHeaderStatus.jsx`: `HACK MODE | PANEL: … | USB: … | CONNECTED` / `BUILD MODE | …` — the mode name is the only difference. PANEL and USB are click-to-cycle **display-only** toggles, cycling `port_aliases` / MAC ↔ panel name; clicking changes no device state and sends no frame.

**The canonical trainer serial path** (`app/hardware/serial_alias.py`) is the USB field's alternate representation and the vocabulary the courseware uses. The trainer deploys to a Raspberry Pi, so the instructional Hack Mode commands speak `/dev/ttyUSB0` (`TRAINER_CANONICAL_SERIAL_ALIAS`) no matter what the dev host enumerates the same board as — `port_aliases` is therefore `(actual port, CLI label if different, canonical path)`, deduplicated, so Windows shows `COM3 ↔ /dev/ttyUSB0`, a Pi already on `/dev/ttyUSB0` shows one value, and a Pi on `/dev/ttyACM0` shows `/dev/ttyACM0 ↔ /dev/ttyUSB0`. **It is a label, never a device**: `DeviceState.port` always holds the real detected port, nothing opens or flashes to the canonical path, and `resolve_serial_target(target, state)` — the seam the later Hack serial engine plugs into — maps a student's canonical target back to `DeviceState.port` *before* any serial I/O, returning None rather than guessing when it matches neither. The build/flash path never reads aliases at all (it uploads to the port discovery returned). `SerialDevice.vid`/`pid` remain parsed as backend diagnostics but are deliberately not student-facing. The status field collapses the backend's richer internal vocabulary to only `CONNECTED`/`DISCONNECTED`, reports the **ESP32 and never the WebSocket**, and shows `—` for both fields when nothing is attached. Build Mode's `state.hardware` block and Hack Mode's `hardware` frame now carry the *identical* `DeviceState.snapshot()` payload, which is what lets one component render both. Hack Mode's frame is **dedicated** precisely so polling is **silent** — never xterm.js output, a `ScenarioEvent`, scenario state, or a router dispatch; `tests/test_websocket_hardware.py` asserts that frame-by-frame. Board-name fallbacks stay backend-side and per-mode (Build Mode its project board, Hack Mode `config.HARDWARE_BOARD_LABEL`). `DeviceState.port` is what Hack Mode's serial transport opens (below).

**Hack Mode's terminal talks to the real ESP32 over USB serial** (Phase 2A, `backend/app/hardware/serial_transport.py`). The path is `xterm.js -> /ws/hack -> command router -> SerialTransport -> pyserial -> ESP32`, and back. `SerialTransport` is per-session (`HackSession.serial`), opens nothing until a command asks, and reads on a **dedicated thread** that parks in the OS driver — pyserial is blocking and has no asyncio interface, so this is what keeps the event loop free; writes go through `asyncio.to_thread`. Bytes surface as `SerialEvent`s on a bounded queue (oldest dropped under flood); `app/websocket.py`'s `_pump_serial` task drains it, decodes through one stateful `SerialTextDecoder` (reassembling a CRLF or a UTF-8 char split across reads, normalising to CRLF for raw-mode xterm) and forwards them as **ordinary `output` frames** — which is why the frontend needed no change at all. A lost board becomes one controlled notice line, never an exception.

Four commands, registered in the same closed allowlist as every simulated tool: `serial-status` (read-only, opens nothing), `serial-monitor`, `serial-send <text>`, `serial-close`. They are the first `async def` handlers — `CommandRouter.dispatch` awaits a handler result if it is awaitable, so the eight synchronous simulated tools were untouched. A student may name the canonical `/dev/ttyUSB0`, but `serial_common.resolve_target` maps it through `resolve_serial_target` to the **real `DeviceState.port`** before the transport sees it; an unresolvable target is refused rather than guessed.

**STILL NOT A SHELL.** Serial input reaches a UART and nothing else. The parser already rejects shell metacharacters and control characters, the registry is a closed table, and no module on this path may use `subprocess`/`eval`/`exec`/`shell` — `tests/test_hack_backend.py`'s repo-wide scan covers the new modules with no exemption, and `tests/test_serial_transport.py` re-asserts it for the transport specifically. A payload like `"rm -rf /"` is transmitted as inert bytes; what the firmware does with them is the firmware's business.

**TEARDOWN MUST NOT AWAIT.** The server cancels the endpoint task on disconnect, so every `await` in the cleanup `finally` raises `CancelledError` immediately and abandons the rest. An earlier version awaited and therefore leaked both the serial port (blocking Build Mode from flashing that board) and the session registry entry. Cleanup is now three synchronous calls — `pump.cancel()`, `SerialTransport.release()`, `SessionManager.discard()` — and `tests/test_serial_commands.py` pins that.

**Hack Mode activity is recorded server-side and persisted** (Phase 2B, `backend/app/events/`). The chain is `student action → FastAPI → command router → HackEventRecorder → SQLite`, and the recording happens in `app/commands/router.py::dispatch` — the one place where a command's identity, its exit code, and the `ScenarioEvent`s it caused are all in scope. **Nothing is inferred from xterm.js output**: an event exists because `app/scenarios/environmental.py` decided a transition occurred, which is why a bad publish records `spoof_attempted` + `spoof_rejected` and has no path to `spoof_succeeded`. Timestamps come only from `app/events/clock.py` (timezone-aware UTC, ISO 8601); a client-supplied time is never accepted, and `to_iso` *raises* on a naive datetime rather than guessing.

Three row shapes (`app/events/records.py`): `hack_sessions` (the `started_at` anchor Phase 2E's TTE measures from, written at connect, `ended_at` stamped in the WebSocket teardown), `hack_commands` (every submitted line — name, argv, exit code, and `handled`, which separates "no such tool" from "the tool ran and failed"), and `hack_events` (domain transitions, carrying the scenario's own vocabulary verbatim). Commands and events are separate rows on purpose: most attempts are not transitions, and the failed ones are exactly what an evaluator needs. They share **one per-session sequence counter**, so merging them recovers the true interleaved order even inside a single clock tick — `timeline_for_session` does that. Isolation is structural: one `HackEventRecorder` per `HackSession` (built in `__post_init__`), every row carries its session id, and every read is session-scoped — there is no "all events" query. Storage is `SqliteEventStore` (stdlib `sqlite3`, WAL, one lock-guarded connection, append-only), and **a store failure can never break a terminal**: records land in memory first and `StoreError` is absorbed and counted (`recorder.store_failures`). `EventMessage` carries `occurred_at`/`sequence` (protocol v5) so the Activity Log renders the same row the database holds instead of the browser's own clock.

**Hack Mode is a generic engine over a closed, categorized command registry, not a Panel-specific one** (Phase 2C). `CommandSpec` (`app/commands/base.py`) carries a `category` (`CommandCategory`: `firmware` / `network` / `mqtt` / `serial` / `trainer`), and `help` renders the registry grouped by it (`app/commands/registry.py::CommandRegistry.by_category`) — display metadata only, consulted nowhere in dispatch. The load-bearing genericity was already true before Phase 2C formalized it: every non-serial tool handler (`nmap`, `mosquitto_sub`, `mosquitto_pub`, `esptool.py`, `strings`, `grep`) is a thin adapter that parses arguments and calls exactly one method on `CommandContext.scenario` — never a literal IP, topic, or panel id. `Scenario` (`app/scenarios/base.py`) is the extension seam: a future training activity is a new `Scenario` implementation registered in the scenario selector (`app/scenarios/registry.py`, Phase 2D.3 — see below), not a new `if panel_id ==` branch inside a handler or the router. PHASE 2C FINALIZATION replaced the earlier placeholder `firmware-extract`/`firmware-analyze`/`mqtt-explorer` commands (none of them real tools) with real-tool semantics: `esptool.py read_flash <offset> <size> <file>` (only that one subcommand is modeled) calls `Scenario.extract_firmware()`; `strings <file>` and `grep <pattern> <file>` both call `Scenario.analyze_firmware(search)` — `strings` with `search=None` for an unfiltered dump of every printable string, `grep` with the student's pattern for a filtered one, silent with a non-zero exit when nothing matches, exactly like real `grep`. `mqtt-explorer` was removed outright rather than renamed: it was never a real tool, and its topic-browsing role is already covered by `mosquitto_sub`. `history` (Phase 2C) is the fully generic trainer utility completing that category: it reads `context.session.recorder.commands` (Phase 2B, in-memory, per-session) back to the student and imports nothing from `app.scenarios`. None of this introduces a new `ScenarioEventType` — the canonical 11-member vocabulary from Phase 2B/normalization (`scan` included, `mqtt_service_scanned` never reintroduced) is unchanged; every command above is recorded purely as `HackCommandRecord` rows through the same Phase 2B seam every command already went through.

**Validation still does not exist**, and neither do the later Hack phases: no *real* MQTT client, no *real* nmap, no *real* firmware extraction (every tool above is fully simulated against in-memory `ScenarioState` — see `app/scenarios/environmental.py`), and **no scoring** — Phase 2B records facts only; no metric formula (ACR/RE/EAC/TTE, TTR/AID/DEI) is computed anywhere. The simulated scenario engine is untouched and still drives every non-serial command.

**Build Mode is a real backend-backed workspace with real compilation, not a mock.** `BuildMode.jsx` connects to `/ws/build` via `src/hooks/useBuildSocket.js`. The backend (`backend/app/build/`, `backend/app/build_sessions.py`, `backend/app/build_websocket.py`) owns one project per session, represented as an ordered sequence of locked/editable regions (`backend/app/build/models.py`, `workspace.py`). The default project a fresh session loads is the **LED Blink pipeline-proof project** (`backend/app/build/blink.py`, project id `led-blink-poc`) — a deliberately trivial one-file, one-editable-region firmware whose only job is to prove the write → compile → flash → physical-execution pipeline works end to end against a real ESP32. The earlier Environmental Monitoring / Weak MQTT firmware (`backend/app/build/environmental.py`, `create_environmental_monitoring_project`) predates the finalized five-panel scope and is no longer loaded by default; the module remains in the codebase, unused, for when that scope resumes. Only the one editable region can be edited (named `security_logic` on the environmental project, `blink_program` on the current default); the backend rejects any attempt to edit a locked region or an unknown region id, regardless of what the frontend sends. A `compile` request runs the real `arduino-cli` (`backend/app/build/compiler.py`, which builds the argument array and hands it to `backend/app/build/process.py` — the one module in the whole backend allowed to spawn a process, and the one both the compiler and the flasher go through) against a throwaway materialized copy of the workspace — `compile_status` moves through `not_started`/`running`/`succeeded`/`failed` for real, driven by the actual compiler exit code, and `compile_output` carries its real stdout/stderr back to the UI.

A `flash` request runs the real `arduino-cli upload` (`backend/app/build/flasher.py`) against a **physically connected ESP32**, so it needs real hardware attached. The backend discovers the serial device itself via `arduino-cli board list` and never lets the frontend name a port, executable, binary, or flag — the `flash` frame is field-less. Flashing requires a successful compile whose retained build output still matches the workspace by content hash (`BuildSession.flash_ready`), so editing the region after a green build disables flashing until it is compiled again. `flash_status` adds two members `compile_status` does not have: `detecting`, and `no_device` as a terminal state distinct from `failed`, because "no ESP32 is plugged in" must never be presented as a build or toolchain problem. A successful flash means the upload process exited 0 — nothing more.

Validation is still not implemented: nothing connects to MQTT, reads sensors, re-runs Hack Mode, or checks whether the remediation actually works. `validation_status` stays always `"not_started"`, and the Validate/Security-Test controls in the UI are disabled placeholders.

**Dashboard charts are hand-rolled inline SVG/CSS** (`BarChart`, `LineChart`, `RadarChart` inside `Dashboard.jsx`) — no charting library is used.

**Styling**: a single global `src/App.css` (~800 lines) plus a small `src/index.css` reset. No CSS modules, no Tailwind, no styled-components — class names are plain strings shared across screens (e.g. `.page`, `.panel`, `.btn-solid`, `.link-footer`).

**No routing library, no state management library, no backend/API calls.** Login, registration, and evaluation "lookups" are all synchronous in-memory array searches against `registry` (in `App.jsx`) or `STUDENTS` (in `data.js`) — nothing is persisted across a page reload.
